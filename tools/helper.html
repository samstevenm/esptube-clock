ℹ️ How the serial link works
      
    
        
  • Cable: the clock powers and enumerates only through a powered USB hub (it draws more than a laptop port gives). The port shows up as usbserial-XXXX; the number follows the hub port.
    • 
        
  • Opening the port resets the clock — the flasher's auto-reset circuit fires on the DTR line. You'll see the boot log (~6 s), then the shell answers. Not a fault; handy for catching boot problems.
    • 
        
  • Shell: plain text, one command per line; help lists them. Same engine as the REST API (status = /status, preset 0 = /preset/0), so anything the web can do, the cable can do — with no WiFi at all.
    • 
        
  • WiFi from the cable: wifi (status) · wifi scan · wifi list · wifi add "Name" pass · wifi forget Name · wifi join Name · wifi ap on|off (recovery hotspot esptube-setup, password esptube-setup, 192.168.4.1) · wifi appass … · wifi reconnect. The clock remembers up to 8 networks and joins the strongest one it sees; with none in range it raises the hotspot by itself (also: menu → AP). rtc shows the battery-backed clock chip that keeps time without WiFi (rtc set writes the current time to it).
    • 
        
  • Debug modes: fps prints draw timings and stream stats; sweep runs the all-times test (it announces TEST on the glass first); wifi shows the link; token <t> sets the stream token; baud <n> switches speed (then reconnect here at that speed).
    • 
        
  • The cable as the control link: with control over the cable on auto, the moment the clock stops answering over the network every control on this page (faces, messages, LEDs, brightness, time, WiFi) is sent as a shell line and every pixel push / 📹 Live frame as an ESP/1 frame on this port — no bridge, no WiFi. It switches back to the network by itself when the clock answers again. Per-tube glow and text over the cable aren't supported (yet).
    • 
        
  • Speed: 115200 baud is ~10 KB/s — a 16-colour tile every ~0.7 s. ⚡ Fast link finds the fastest rate this cable really does (it tells the clock baud N, reopens the port — the clock comes up at N for that one reset — and checks that help answers, stepping down 460800 → 230400 → 115200). Nothing is saved on the clock: a power cycle is always 115200. This USB chip could not do 921600.
    • 
        
  • One owner at a time: if tools/monitor.sh, the bridge or PlatformIO holds the port, the browser can't open it (and vice-versa). Disconnect here before flashing over USB.
    • 
        
  • Crashes: a Guru Meditation Error line plus a Backtrace: — 💾 save the log and decode it: xtensa-esp32-elf-addr2line -pfiaC -e firmware.elf <addresses> (toolchain under ~/.platformio/packages/).

ℹ️ How pushing works
    
Full frames are pushed as RGB565 to /raw565 (the memory-safe path;
      BMP /image is never used — it crashes the clock). Across 5 tubes this runs
      ~1–3 fps (bandwidth-bound) — design screen animations to look good slow. LED effects
      (Rainbow/Breathe/…) use the cheap 3-byte /rgb primitive and run much faster.
      Only tubes whose pixels changed are re-sent.

    

  


  
  

    
🔧 Flashing & tools terminal commands · copy & run

      
HTML can't flash the ESP32 — run these in a terminal
        from the tools/ folder. Copy with the buttons. (For everyday poking over the cable, the 🧷 USB serial panel above replaces monitor.sh.)

      
./flash.sh                # build + USB-flash (default port /dev/cu.usbserial-1220)

      
./monitor.sh              # serial console @115200 (Ctrl-C to quit)

      
pio run -d ../firmware/custom-fw -e esptube -t upload --upload-port esptube.local
                          # OTA update over WiFi (no cable)

      
./esptube status          # pretty-print /status  (set ESPTUBE_IP or use esptube.local)
./esptube text 0 HI       # quick CLI poke (tube 0 = far right)

      
The clock also serves its own on-device panel at http://esptube.local.
        This helper is a richer, offline-first companion.
